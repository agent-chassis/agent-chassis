
# Host Write-Authority Localhost Sidecar Endpoint Contract

> Part of the [Agent Launch & Direct-Dispatch Reference](agent-launch-quickstart.md).

This page is the durable owner of the launcher-owned host-write-authority dispatch sidecar transport contract: endpoint ownership, the loopback-only and kernel-assigned-port invariants, dead-sidecar recovery, the structured blocker, and the redaction surface.

## Host Write Authority Localhost Sidecar Endpoint Contract (initiative)

This subsection is the durable owner of the launcher-owned
host-write-authority dispatch sidecar transport contract. It pins AUTH-H3
(`endpoint-contract-unowned`). Authority hardening here is secondary to working
structured dispatch; this contract must not introduce a new launch precondition
for the controlled-orchestrator path.

**Startup ownership.** The endpoint is launcher-owned startup transport state,
not agent input. `agent-launch orchestrator` / `agent-launch resume` start a launcher-owned
localhost sidecar outside the orchestrator bwrap namespace before spawning the
orchestrator child, bind it, read back the kernel-assigned port, and write the
resolved value into the orchestrator child env. MCP startup reads it once,
before the MCP transport is wired. It is never accepted from prompt text,
request payload, argv, `claimed_identity`, or agent-authored environment
carriers.

**Canonical endpoint variable.** The canonical endpoint env var string is:

- `AGENT_LAUNCH_HOST_WRITE_AUTHORITY_TCP_ENDPOINT`

Its value shape is `<loopback-host>:<kernel-assigned-port>`. The JS
identifier `HOST_WRITE_AUTHORITY_SIDECAR_ENDPOINT_ENV_VAR` in
`host-write-authority-substrate.mjs` is a misleadingly named constant whose
string *value* is exactly `AGENT_LAUNCH_HOST_WRITE_AUTHORITY_TCP_ENDPOINT`.
There is no second competing endpoint env var; this is identifier/value naming
drift only, not two live env-var strings.

**Loopback-only invariant.** The endpoint host is pinned to IPv4 `127.0.0.1`.
Non-loopback hosts (`0.0.0.0`, `::`, `::1`, any routable address) are refused
before listen/connect. IPv6 (`::1`) is intentionally unsupported until a later
WK explicitly adds and tests it.

**Kernel-assigned per-orchestrator ports; static ports forbidden.** Each
orchestrator startup binds loopback with a kernel-assigned port.
Static/fixed ports are forbidden and refused before listen. Each orchestrator
session gets its own cache directory, endpoint, run-id namespace, and monitor
handles, so multiple orchestrators on one host — each dispatching multiple
concurrent workers, reviewers, and redteam agents — do not collide on
endpoint, cache, authority-file, run-id, or monitor-handle state.

**No controlled-orchestrator Unix-socket fallback.** Controlled-orchestrator
MCP startup must not fall back to the legacy `.local/state` Unix-socket broker
when `AGENT_LAUNCH_HOST_WRITE_AUTHORITY_TCP_ENDPOINT` is absent, malformed, or
unreachable. The resolver consults only the localhost endpoint; a missing
endpoint returns no adapter, and the in-process executor surfaces the
structured blocker below. This closes AUTH-H1 (`dead-unix-socket-fallback`)
for the controlled-orchestrator path. Any remaining operator-shell socket
compatibility is not yet supported and must not be reachable from
controlled-orchestrator MCP startup.

**Dead-sidecar recovery and structured blocker.** A configured-but-dead,
unreachable, refused, unauthorized, or malformed sidecar is reported only by
dispatch/`startLaunch` as the structured runtime blocker
`backend_unavailable` with reason `host_write_authority_substrate_unavailable`.
Static dispatch-readiness must not probe the sidecar for liveness (this closes
AUTH-H4, `readiness-runtime-conflation`). Recovery is to start a fresh
launcher-owned sidecar (restart `agent-launch orchestrator` / `agent-launch resume`); a dead
sidecar is never a reason to fall back to wrappers, direct CLIs, shell, temp
worktrees, broad bwrap remounts, inline env policy, a stdio auth prelude, a
connection registry, Unix-socket fallback, or a graph-impact launch side
channel.

**Authority file (AUTH-H2).** The
optional per-orchestrator authority file is named by:

- `AGENT_LAUNCH_HOST_WRITE_AUTHORITY_FILE`

It is generated by the launcher in the per-orchestrator orchestrator cache and
is launcher-owned transport state, never accepted from prompt, request, argv,
`claimed_identity`, or agent-authored environment. Authority-file enforcement is
not a standalone launch prerequisite unless the touched channel surface
implements it end to end (broker server side and MCP adapter side together).
The active contract relies on launcher-owned endpoint minting, loopback-only
binding, request-source rejection, and WK-derived bwrap isolation for accepted
launches; authority-file values remain redacted wherever they leave the
launcher-owned boundary.

**Operator-shell socket variable.** `AGENT_LAUNCH_HOST_WRITE_AUTHORITY_SOCKET`
is operator-shell-only and is never read by controlled-orchestrator MCP
startup. It selects the legacy Unix-socket operator broker path only; the
controlled-orchestrator dispatch path ignores it entirely.

**Redaction surface.** Endpoint and authority-file values must be redacted
across every surface that can emit them: planner / `--dry-run-json` output,
broker/server logs, channel errors, MCP dispatch responses,
`workspace_agent_run_status` `final_result` envelopes, structured blocker
detail fields, and WK closure / attempt-log text.

## Deterministic Managed Worktree Provisioning Over The Broker (work record, work record)

Managed dispatch previously ran `provisionManagedWorktreesAtDispatch` inside the
read-only orchestrator wiki-MCP namespace before control reached the writable
host-write-authority broker, so `git worktree add` failed while creating the WK
branch lock under the main repo's read-only `.git/refs`. work record moved the
initial implementation path across the existing host-write sidecar boundary so
the broker performs it from its writable host namespace. MCP remains stdio-only
(decision); this reuses the already-running host-write transport and adds no
listener, HTTP/URL transport, bearer/token/authentication system, proxy, relay,
daemon, second broker, generic Git API, or worker-visible Git metadata.

The governing operation is retry-invariant: after independent liveness admission,
every accepted exact-slice dispatch ensures or continues the deterministic slice
branch and v2/full slice worktree. The WK branch `wk/IN/WK` and persistent WK
worktree are separate WK-level resources. The slice branch is durable authority
and the slice worktree is a reconstructible view (decision); physical presence
determines create, checkout, or reuse mechanics only. Failure cause, attempt
history, retained bindings, and `retry_id` do not select another provisioning
path (work record).

The current WK branch tip is consulted exactly once only when both the slice
branch and slice worktree are absent, so the missing slice branch can be created
at that tip. An existing slice branch is continued from its exact current tip:
when its slice worktree is absent the broker checks out that branch, and when a
correctly-associated clean full slice worktree is present the broker reuses it.
A present slice worktree path without its slice branch, wrong association,
malformed Git state, a physical sparse/v1 checkout, or staged, unstaged, or
untracked content refuses before destructive mutation or worker launch. A later
WK branch tip is never continuation authority for an existing slice branch.

**One `provision_worktree` operation.** The host-write protocol gains exactly one
operation, `provision_worktree`, and one response kind, `worktree_provisioned`.
The broker invokes the existing `provisionManagedWorktreesAtDispatch` primitive
(injected, never reimplemented) and returns its complete launcher-owned
`managed-worktree-binding.v1` carrier. Every non-negative integer `retry_id`
uses this same ensure operation when the host-write provisioning adapter is
configured; without that adapter, every retry uses the direct writable-host
ensure operation. Transport choice is launcher-owned composition, never retry
identity. work record owns ambiguous broker-response recovery only, not same-slice
checkout semantics.

**Launcher-owned roots, request carries only identity.** The broker resolves its
canonical `mainRepo` and `worktreeRoot` from launcher-owned production
composition — the orchestrator plan's repo (the `.agent-worktrees/<repo>`
sibling), frozen before launch — plus the injected provisioner. These roots and
the provisioner NEVER come from the MCP request, worker, prompt, argv,
environment, cwd, claimed identity, or a returned carrier. The
`provision_request` payload carries only the server-resolved per-attempt identity
(`role`, `subject`, `initiative`, `launch_ref`, `run_id`, `retry_id`); an
extended, missing, non-worker, non-slice, negative, or non-integer payload is
refused before the provisioner runs. A broker not composed with those roots +
provisioner refuses `provision_worktree` with
`broker_provisioning_unavailable`.

**Exact carrier validation and deep refreeze.** The MCP-side provisioning adapter
validates the response envelope, proves the returned carrier is the complete,
exact-schema, internally-consistent `managed-worktree-binding.v1` object for the
requested non-negative integer retry identity, proves that the outer carrier and
both nested bindings preserve that exact identity, proves it survives JSON
encoding unchanged (lossless), and
deep-refreezes it (JSON cannot carry `Object.freeze` metadata). A malformed,
extended, mismatched, or lossy carrier fails closed with
`host_write_authority_provisioning_carrier_invalid`
(`operator_recovery_needed`). The dispatch backend then feeds the validated
carrier unchanged into the existing `start_launch` path and re-runs the same
current-attempt and frozen-scope-authority re-verification it applies to an
in-process carrier before recording the binding or spawning the worker.

Remote agent runner distribution and its endpoint/authority handling are out of
scope for this local sidecar contract.

## Admissibility Is Decided Once By CCE; The Broker Is A Trusted Executor (work record)

Worker admissibility is decided exactly once, by CCE, on the dispatch/backend path:
dispatch readiness returns a ratified pack-backed `admit` (or the sole positive
`local_only_fail_open` posture), and that is the single admissibility authority. The
host-write-authority broker does **not** re-decide it. The broker is a trusted
executor: on `start_launch` for a worker it trusts the CCE admit already rendered on
the dispatch path and proceeds to provision → plan → spawn, with frozen-`write_scope`
enforcement owned by the closed-input `commit_slice` path. It renders no admissibility
verdict, loads no canonical record for admission, computes no admission digest, and
performs no CCE re-consult. The transport is the trust boundary.

This retires the earlier stopgap (work record/work record) in which the broker independently
re-consulted CCE with its own bootstrapped Node Engine env, and moots the
carrier-digest re-read the broker performed to bind that re-consult (work record): the
broker no longer re-reads or re-hashes the canonical record on the launch path, so the
worktree-vs-mainRepo digest, dirty-record digest, and sparse-worktree CCE-config
fragilities that class introduced are gone. `broker_worker_admission_refused` is no
longer emitted as a launch gate. The broker still derives one worker-branch fact — that
a launch is a launcher-proven managed worker, signalled by the launcher transporting a
frozen scope authority — solely to gate the managed-worker endpoint projection below;
that derivation reads only the transported scope authority, never a record.

A cryptographically-verifiable signed admit that the broker could positively verify
(rather than merely trust the transport) is optional future hardening (work record); it is
**not** built here and is not required for this posture.

### Managed-Worktree-Binding Carrier Field Set And Trusted-Side Topology Derivation (work record)

The `managed-worktree-binding.v1` carrier that crosses the `start_launch` wire has an
exact field set. Its outer `schema_version` (`managed-worktree-binding.v1`) is unchanged
across the checkout modes below; the checkout-density facts are the only
mode-discriminated part. Under the decision sparse→full rollout the carrier is EXACTLY
one of two discriminated shapes, and the channel proves each is complete and exact —
anything mixed, extended, or unknown fails closed:

- **`v1` legacy sparse.** The outer carrier carries exactly: `schema_version`, `complete`,
  `main_repo`, `initiative`, `record_id`, `slice_id`, `unit_address`, `retry_id`,
  `wk_binding`, `slice_binding`, `worktree_path`, `output_branch`,
  `base_ref`, `base_sha`, `write_scope`, `cone_dirs`, `index_sparse`,
  `validation_worktree_path`, and `shared_git_exposed`.
- **`v2` full (decision).** The outer carrier drops the sparse pins `cone_dirs` and
  `index_sparse` and carries the launcher-owned discriminant `checkout_mode` (value
  `"full"`) in their place; every other outer field is identical to `v1`.

The nested `wk_binding` is mode-independent — the whole-WK validation binding is always
the bare exact shape carrying exactly the 14 fields `schema_version`, `launch_ref`,
`run_id`, `retry_id`, `unit_address`, `initiative`, `record_id`, `slice_id`, `base_ref`,
`base_sha`, `output_branch`, `worktree_path`, `write_scope`, `write_scope_source`. The
nested `slice_binding` carries those 14 plus `read_scope`, `repo_paths`, `selected_unit`,
`source_digest`, `source_version`, and then its mode-specific checkout facts: a `v1`
sparse slice binding (identity `schema_version` `worktree-identity-binding.v1`) adds
`cone_dirs` + `index_sparse`; a `v2` full slice binding (identity `schema_version`
`worktree-identity-binding.v2`) adds `checkout_mode` (`"full"`) instead. The slice
binding's checkout markers are PAIRED with its identity `schema_version`, and the outer
carrier mirrors the slice binding's mode; a marker/version disagreement (for example
`checkout_mode="full"` under `worktree-identity-binding.v1`) fails closed. The channel
proves each nested binding carries **exactly** its declared field set, so no extra or
authority-shaped field can enter through a nested binding.

Checkout density is launcher-owned: it is never selected by request payload, prompt,
argv, environment, or a caller-supplied carrier, and confinement is the bwrap namespace,
not the checkout density (a full checkout does not widen the worker's exact `R∪W`
namespace). The carrier, broker-channel, adapter, commit consumers, and public backend
all ACCEPT both discriminated shapes fail-closed. Minting is now ACTIVATED on `v2`: the
work record SLICE-006 flip made the launcher-owned FULL allocator the new-checkout
default, and SLICE-009 CLOSED the injection seam, so both managed compositions mint
a `v2` FULL slice worktree whenever they create a slice checkout. Every retry
reaches that same ensure path without reopening the density seam.

The seam is closed on two halves, and only both together make the drain complete rather
than merely renamed:

- **By name** — the legacy `allocateSparseExactUnitWorktree` dependency key is no longer
  honored for new checkout allocation in either composition
  (`worktree-provisioning-dispatch-managed.mjs`, `backend-worktree-binding.mjs`), so no
  caller, config, or test can select the legacy allocator by that name.
- **By output** — the surviving `allocateFullSliceExactUnitWorktree` injection point
  (retained so failure-injection suites can still make allocation throw) is PROVEN to
  have returned the `v2`/`full` shape: a new allocation whose slice binding is not
  `worktree-identity-binding.v2` + `checkout_mode="full"` fails closed into the normal
  compensating rollback. Supplying the sparse allocator UNDER the full key therefore
  refuses instead of minting `v1`. Density is positively proven from the binding, never
  inferred from which dependency key was read.

No provisioning path — production or injected — mints a new `v1` sparse slice
worktree. Stale v1 binding evidence does not select reissue and, when neither
physical slice resource exists, does not block creation of the current v2/full
slice worktree. A physically present sparse/v1 slice worktree is unsupported and
refuses; provisioning does not adopt, convert, reset, preserve, or silently reuse
it. Legacy v1 remains accepted only by separately-owned drain consumers for
already-published carriers; it is not an ordinary-continuation provisioning
algorithm.

The same-unit liveness gate remains independent of provisioning. A live or
indeterminate prior worker refuses before the broker/direct ensure call; terminal
prior state permits that same operation. Git resources, retry identity, bindings,
and attempt classifications are not liveness evidence. Before successful result
publication, compensation tracks created-versus-reused resources out of band and
removes only slice resources created by that transaction. It preserves reused
slice resources, the WK branch, persistent WK worktree, and all existing commits.
Lost responses, broker restart after publication, and spawn/registration
ambiguity remain work record/work record concerns.

The former caller-carried `provisionedWorktreeGitBinding` /
`provisioned_worktree_git_binding` launch-input aliases are **deleted** — a decision-style
deletion, not a compatibility mirror. They are removed from the host-write allowlist, the
envelope sanitizer's alias mirroring, and the broker-channel presence/agreement
requirement; a launch input carrying either spelling refuses as a non-schema field before
serialization. The linked-worktree Git topology (`worktreePath`, `gitDir`, `mainGitDir`,
`gitPointerFile`) is instead derived at the trusted broker plan-launch boundary
exclusively from the validated carrier's `main_repo` and `worktree_path`, matching the
launcher's own `provisionedWorktreeGitIdentity` derivation, and only after the channel's
exact-schema/freeze/losslessness proofs and the pre-preparation current-attempt binding
(including the `workspace_dir` presence-and-equality requirement) succeed. Realpath /
symlink hardening of those derived paths remains work record.

## Managed Worker Closed-Input Commit Over The Broker (work record)

A managed implementation worker's only delivery authority is the closed-input
`commit` MCP tool exposed in its confined stdio wiki-MCP child. That child runs
inside the Git-less managed namespace, so it cannot run `git` itself. The commit
is therefore delegated across the existing host-write sidecar boundary so the
broker performs it from its writable host namespace. MCP stays stdio-only
(decision); this reuses the already-running host-write transport and adds no
listener, HTTP/URL transport, bearer/token/authentication system, proxy, relay,
daemon, second broker, generic Git API, or worker-visible Git metadata. The
worker's MCP tool surface stays exactly `{commit}` and its input schema stays the
strict empty object.

**One `commit_slice` operation.** The host-write protocol gains exactly one
operation, `commit_slice`, and one response kind, `slice_committed`. The request
carries only the launcher-minted per-run identity — `{ assigned_unit, launch_ref,
run_id, retry_id }` — resolved from launcher-owned configuration projected into
the worker's stdio wiki-MCP child. It carries no caller-selected repo, worktree,
ref, branch, base SHA, write_scope, tree, commit, message, Git args, command,
mode, or identity override; those are dropped by the request builder and the
broker's exact outer/inner envelope guards. An extended, missing, non-canonical,
or negative-`retry_id` payload is refused (`broker_commit_request_invalid`)
before any Git operation.

**Launcher-owned root, server-side binding resolution.** The broker resolves its
canonical `commitMainRepo` from launcher-owned production composition (the same
launcher-minted `mainRepo` used for provisioning), never from the MCP request,
worker, prompt, argv, environment, cwd, or claimed identity. It independently
reads the exact frozen slice binding from the identity store under that canonical
root, re-verifies it against the launcher-assigned unit (unit_address, initiative,
record/slice ids, selected_unit, and output_branch), and then runs the EXISTING
content-inert `materializeCommitObject` / `verifyAndMeasureCommitScope` /
`commitSliceRef` primitives — never a second commit implementation, a generic Git
surface, or a worker-selected message (the message is server-generated). A stale,
mismatched, sibling, or absent binding, or a Git failure, fails closed
(`broker_commit_threw`) with zero ref mutations. A write-scope containment failure
refuses (`broker_commit_scope_refused`) before advancing any ref. A broker not
composed with the canonical root + commit primitive refuses
(`broker_commit_unavailable`). Successful delivery advances only the exact slice
ref; trusted runtime still owns slice-to-WK integration and freezing the
accumulated whole-WK review target.

**Endpoint projection is worker-only.** The launcher projects the host-write
endpoint into a MANAGED worker's stdio wiki-MCP child config (as a Codex
`-c mcp_servers.wiki.env.AGENT_LAUNCH_HOST_WRITE_AUTHORITY_TCP_ENDPOINT="..."`
override) ONLY when that worker carries the commit tuple. Reviewer, redteam,
orchestrator, direct/unmanaged, Claude, Agy, configured-command, and
configured-URL paths never receive the endpoint and never gain the
managed-worker commit operation. When no endpoint is projected (unmanaged/direct/
legacy), the worker's `commit` tool runs the existing in-process pipeline
unchanged.

**Adapter fail-closed.** Before calling the broker, the MCP-side commit adapter
requires the complete launcher-minted `assigned_unit` / `launch_ref` / `run_id` /
`retry_id` request identity. On success it accepts only the exact closed
`commit_result` field set, requires canonical Git object IDs, and binds the
returned `assigned_unit` and canonical slice ref to the requested unit. The
broker independently owns same-attempt tuple freshness through its server-side
binding resolution; the response does not add an untrusted tuple echo. The
adapter also proves that the result survives JSON encoding unchanged (lossless)
before deep-freezing it. An extended, partial, sibling-unit, wrong-ref,
malformed-object-ID, not-committed, submit-for-review, or lossy result fails
closed with `host_write_authority_commit_result_invalid` — never a false success
and never a Git fallback in the confined namespace.

## Post-Terminal Slice-to-WK Integration Over The Broker (work record)

After a managed implementation worker terminates and its closed-input `commit_slice`
advances the slice ref, trusted runtime must integrate that committed slice into the
parent WK branch: rebase the slice onto the current WK tip if the base is stale,
advance the WK ref by a pure `update-ref <ref> <new> <old>` CAS (work record — the
former ff-only merge and persistent-worktree advance are RETIRED), and freeze the
accumulated whole-WK review target by moving the canonical parent record to `review`.
On the FINAL slice it then materializes the persistent worktree for review (below).
That work runs `git` (and a canonical work-record status write), so it cannot run
inside the read-only orchestrator wiki-MCP namespace — the work record canary observed it
fail there with `agent_launch.slice_integration.git_failed.v1` even though the commit
had already advanced the slice ref. The integration is therefore delegated across the
existing host-write sidecar boundary so the broker performs it from its writable host
namespace. MCP stays stdio-only (decision); this reuses the already-running host-write
transport and adds no listener, HTTP/URL transport, bearer/token/authentication system,
proxy, relay, daemon, second broker, generic Git API, retry protocol, cleanup RPC,
cached-success registry, or worker-visible Git metadata.

**One `integrate_slice` operation.** The host-write protocol now enumerates exactly
three same-pattern managed-lifecycle write operations — `provision_worktree`,
`commit_slice`, and `integrate_slice` — with the response kinds `worktree_provisioned`,
`slice_committed`, and `slice_integrated`. The broker invokes the existing
`integrateCommittedSlice` primitive (`slice-integration.mjs`, unchanged) and returns its
complete launcher-owned `slice-integration.v1` result plus an echo of the four-field
request tuple and the bound terminal-review attestation described below. The request carries only the launcher-minted per-run identity — `{
assigned_unit, launch_ref, run_id, retry_id }`, the **base** run identity the parent
monitor already tracks. It carries no caller-selected repo, worktree, ref, base/WK SHA,
write_scope, or mode; those are dropped by the request builder and the broker's exact
outer/inner envelope guards. An extended, missing, non-canonical, negative-`retry_id`,
or pre-qualified-`run_id` payload is refused (`broker_integration_request_invalid`)
before any tuple lookup or Git operation.

**Trusted-runtime-only trigger; no trigger authentication.** Unlike `commit_slice`,
which the confined worker's `commit` tool delegates, the worker has **no** integrate
tool. Integration is invoked only by trusted runtime — the parent run-monitor lifecycle
(`dispatch-run-monitor-routes.mjs`), and only after that lifecycle observes the worker
reach terminal outcome **succeeded** (`status.terminal && status.status === "succeeded"`
at the `runPostWorkerSliceLifecycle` gate). The terminal-succeeded gate therefore lives
at the parent, not the broker; a failed or still-running worker never reaches the
integration call. Because nothing but trusted runtime can call the operation, there is
nothing to authenticate: the broker accepts the same loopback residual as
`commit_slice` and adds no trigger credential.

**Launcher-owned root, server-side binding resolution.** The broker resolves its
canonical `integrationMainRepo` from launcher-owned production composition (the same
launcher-minted `mainRepo` used for provisioning and commit), never from the MCP
request, worker, prompt, argv, environment, cwd, or claimed identity. It derives the
`.slice`- and `.wk`-qualified binding identity from the base run id through the same
`bindingIdentity` normalization `commit_slice` uses (a pre-qualified id is refused),
independently re-verifies the slice binding against the launcher-assigned unit
(reusing `verifyExactSliceCommitBinding`), and then runs the existing
`integrateCommittedSlice` pipeline — whose WK advance is a pure `update-ref` CAS, with
no persistent-worktree merge seam — and a host-side canonical review-freeze status
transition. A stale, sibling, or
base/`.slice`-collision tuple resolves no valid binding and fails closed pre-mutation
with zero Git operations. A broker not composed with the canonical root + integration
primitive refuses (`broker_integration_unavailable`).

**Exactly-once with a fail-loud latch.** The broker maintains a per-tuple state machine
created lazily on the first `integrate_slice`: `in_flight -> integrated`, with a
`failed_indeterminate` terminal state. A concurrent duplicate refuses
(`broker_integration_in_flight`) and a post-success replay refuses
(`broker_integration_already_integrated`), both before any Git mutation. A primitive
failure proven pre-mutation releases the gate so a later attempt can retry; a throw
after a mutation that could not be guaranteed reversed (`rebase_restore_failed` or a
review-freeze WK-ref compensation failure) latches `failed_indeterminate`, and every
subsequent request for that tuple refuses (`broker_integration_latched_indeterminate`)
with zero Git mutation. This is fail-loud exactly-once, explicitly **not** work record
response-loss / restart recovery, which is not absorbed. decision integration semantics
are preserved exactly (post-confirmed-termination only; stale-base rebase onto the WK
tip; conflicts fail loud with abort/restore and no automatic slice-ref rollback;
post-work record the WK advance is a pure `update-ref` CAS rather than an ff-only merge)
and work record/decision confinement is unchanged.

**Adapter fail-closed and delegated-result parity.** Before calling the broker, the
MCP-side integration adapter requires the complete launcher-minted request identity. On
success it accepts only the exact closed `slice-integration.v1` result field set —
including the frozen whole-WK `review_target` (its own exact nested schema), bounded
transition evidence, the integrated slice SHA, previous and new WK tips, and the rebase
disposition — validates every represented Git object ID and cross-field consistency,
binds the echoed four-field tuple back to the originating request, proves the result
survives JSON encoding unchanged (lossless), and deep-freezes it. An extended, partial,
sibling-unit, wrong-ref, malformed-object-ID, tuple-unbound, or lossy result fails
closed with `host_write_authority_integration_result_invalid`. The validated result
carries every field the downstream review-freeze consumer needs, so
`bindFrozenReviewContext` and the reviewer dispatch work unchanged from the delegated
result. Direct/writable-host composition (no sidecar endpoint) keeps the existing
in-process integration path.

**Terminal review materialization inside `integrate_slice` (work record / decision
clause 1(b)).** Because the WK advance is a pure `update-ref` CAS, integration orphans
the persistent WK worktree: its index and working files stay at the pre-integration
tree while its ref names the new tip. The managed whole-WK reviewer reads SOURCE in
that physical worktree, so it would review stale code — the work record live
bug. On the FINAL slice only (a non-final slice returns a null `review_target` and
launches no reviewer), `defaultIntegrateManagedWorkerSlice` therefore re-creates the
persistent worktree as a FRESH FULL CHECKOUT at the frozen reviewed SHA at the
EXISTING path (`git worktree remove` then `git worktree add`; never `reset --hard`,
never a sibling directory) and runs the 7-part fail-loud on-disk verification. This
runs HERE because it is worktree Git, which the read-only MCP namespace cannot
execute — the same constraint that routes integration itself through the broker.

The materialize is POST-MUTATION: integration has already advanced the WK ref and
flipped the record to `review`, and the materialize is itself a mutation that cannot
be guaranteed reversed. A failure is therefore re-thrown under the review-freeze code
so the broker latches `failed_indeterminate` rather than releasing the exactly-once
gate for a second integration against an already-frozen WK. The reviewer never
launches, which is the required fail-loud posture.

**The broker is the sole minter of the transported attestation (work record).**
The lifecycle owner cannot mint its own. It runs in the read-only orchestrator
namespace, which mounts the main repo read-only, forbids writable Git roots, and does
not expose the worktree root at all; verify part 5 is `git write-tree`, which
unconditionally takes the index lock. So on the broker route only the broker can
materialize and probe — and it already does. `defaultIntegrateManagedWorkerSlice`
therefore mints a bound proof at that site, strictly after a successful materialize
**and** a successful 7-part verify, and returns it as the result's
`terminal_review_evidence` member.

**The proof is bound, because the bare attestation is not.** The materializer returns
an `agent_launch.terminal_review_materialization.v1` attestation carrying only a
worktree path, WK ref, reviewed SHA, and reviewed tree. That is sufficient for the
broker's own same-call re-assertion but too weakly bound to transport: nothing ties the
on-disk verification to the canonical review target, to the run that produced it, or to
the worktree binding it ran against, so a proof minted for a different run, target, or
worktree would be structurally indistinguishable. The transported
`agent_launch.terminal_review_evidence.v1` envelope wraps the attestation verbatim and
adds three bindings, all **server-resolved**:

- `review_target` — the canonical frozen whole-WK target (unit, ref, SHA, diff
  base/head/range, and both contract flags), computed host-side by
  `integrateCommittedSlice`.
- `run` — the exact four-field run tuple (`assigned_unit`, `launch_ref` as the monitor
  handle, the **base** `run_id`, `retry_id`) the integration ran under, already
  independently re-verified against the launcher-owned binding store.
- `wk_binding` — the launcher-resolved full-WK worktree binding: binding schema, the
  `.wk`-qualified run identity, retry, unit address, output branch, worktree path, and
  the frozen base ref/SHA.

**Exactly one known `.wk` binding schema, at both ends.** The persistent WK worktree
binding is `worktree-identity-binding.v1` and nothing else: decision's
`worktree-identity-binding.v2` discriminant is the SLICE full-checkout carrier, and the
canonical identity-store contract requires the v1 schema for every non-slice unit. The
broker requires that exact version — and the exact canonical 14-field WK shape — before
it mints, and the transport validator requires the same exact version on the wire, so an
unknown, future, slice-shaped (`v2`), mixed (slice `cone_dirs` / `index_sparse` /
`checkout_mode` markers on a WK binding), incomplete, or extra-field binding fails closed
rather than being minted from or accepted as WK evidence. This matters because
`resolveWorktreeBinding` returns the stored JSON verbatim and performs no schema
validation of its own, and because the mint copies only eight of the binding's fields —
so a malformed shape that is not rejected here is silently dropped in transit and
surfaces at the far end POST-mutation, latching `failed_indeterminate` for what is really
a clean pre-mutation binding fault. The mint-site check therefore runs before any
materialize or mutation, and the two ends share the schema literal so they cannot drift.

No field is caller-authored. The request envelope still admits exactly
`{ assigned_unit, launch_ref, run_id, retry_id }` — an integrate request carrying any
additional field (a pre-authored proof, a `deps` injection, a canonical-root or mode
override) is refused with `integrate_request_shape_invalid` before any tuple lookup,
binding resolution, or Git work, and the adapter's request builder drops every
non-whitelisted key before the envelope is built. The broker hands the integration
primitive only its five launcher-owned arguments, so the launcher-owned deps are
unchanged and cannot be substituted by a caller.

**Exactly one proof on a final result, exactly null otherwise.** A non-final slice
launches no reviewer, so it materializes nothing and carries
`terminal_review_evidence: null` — strict identity, so `undefined`, `false`, `0`, `""`,
and `{}` are all refused rather than read as "no evidence". A final result carries
exactly one proof. The adapter's closed field set now admits the member, and
`validateSliceIntegratedResult` enforces an exact closed schema at every level plus
cross-field agreement against the surrounding result: the attestation must record all
seven parts in canonical order with `verified === true`, its ref and SHA must equal the
integrated `wk_ref`/`wk_sha`, the echoed review target must match the result's frozen
target field for field, the run tuple must match the bound request tuple, and the WK
binding must be the `.wk` qualification of that same run at the same retry, naming the
same WK, on the exact worktree path the verification was performed at. A mixed,
extended, partial, unknown-schema, or cross-field-disagreeing shape fails closed with
`host_write_authority_integration_result_invalid`, consistent with the existing
closed-set discipline.

**Threat model — not overclaimed.** This is non-forgeability within the repo's existing
trusted-loopback / honest-launcher model: the broker is the only party that can run the
on-disk verification, it is the only minter, and every bound field is re-derived
server-side, so a cross-run, cross-target, or cross-worktree replay fails the
validator's comparisons. It is **not** a cryptographic guarantee against a hostile
process running as the same user; that would require a challenge/MAC and an
operator-approved authentication-protocol expansion.

The clause-1(b) broker-route surface closes only when the MCP-side guard learns to
require and verify this proof (work record, and the
[dispatch runtime contract](mcp-dispatch-runtime-contract.md)). This half makes the
bound proof exist and arrive; it does not by itself lift the refusal.

## Reaping A Per-WK Branch Requires A Terminal-Disposition Proof (work record, decision clause 4)

The per-WK branch `wk/IN-XXXX/WK-YYYY` ACCUMULATES every integrated slice of a work
record, and the launcher-owned reaper (`worktree-reaper.mjs`, `releaseWorktree`) removes
that branch and its worktree with `git worktree remove --force`, `git worktree prune`,
and `branch -D`. That is the most destructive operation in the managed lifecycle: the
only recovery is the reflog plus the pre-delete tip captured in the reaper's audit sink.

**A caller assertion is not authority.** The reaper was originally specified to remove on
the orchestrator's *finished-assertion* — a `reason` string of `unit-done`, `cancelled`,
or `operator-directed` — with the resolved worktree binding as the only other input. The
SLICE-001 and SLICE-004 redteams ruled that insufficient, explicitly naming the shapes
that do NOT establish a terminal WK: a caller boolean (`releaseRetainedSlice`'s
`reviewResolved`) and its test-only helper, a caller-supplied reason string, the record's
`status`, free-form resolution prose, and run termination on its own. The concrete hole
(M1) is the per-run `.wk` ALIAS binding: the broker derives one for every managed
integration, it resolves to the live accumulating WK branch, and nothing in the old path
distinguished it from a genuinely finished unit. A reap driven from it would delete a
branch with slices still landing and reviews still open.

**Proof B gates every wk/\* reap.** `releaseWorktree` now obtains and validates a
`workspace-agent-wk-terminal-disposition.v1` proof BEFORE audit creation, worktree
removal, prune, and `branch -D`. Its fields are `schema_version`, `record_id`,
`initiative`, `wk_ref`, `verified_wk_sha`, `canonical_record_digest`, `disposition`
(exactly one of `landed`, `terminal_cancelled`, `terminal_reverted`),
`disposition_receipt_id`, `disposition_receipt_digest`, `relevant_run_ids`,
`terminal_run_ids`, `unresolved_review_units`, `unintegrated_units`, `minted_at`, and
`proof_digest`. Validation establishes, together and all pre-mutation:

- **Binding** — the proof's record, initiative, and WK ref agree with the resolved
  binding; its `verified_wk_sha` equals the ref's tip read live at gate time; and its
  `canonical_record_digest` equals the digest recomputed from the canonical work record
  on disk right now. A stale tip or a record edited since minting fails here.
- **Quiescence** — every id in `relevant_run_ids` appears in `terminal_run_ids`, so no
  relevant worker or reviewer run is still live.
- **Review** — `unresolved_review_units` is empty. The reaper never trims a branch under
  unresolved review.
- **Completeness** — `unintegrated_units` is empty: every needed implementation slice is
  integrated or explicitly cancelled/reverted.
- **Disposition** — the disposition is one of the three enumerated terminal outcomes and
  its `disposition_receipt_digest` re-derives from the bound facts (record, initiative,
  ref, verified SHA, receipt id), so a disposition string cannot be self-asserting or
  lifted from another WK.

Each failure raises its own stable code —
`agent_launch.worktree_reaper.wk_terminal_proof_{missing,malformed,binding_mismatch,workers_not_terminated,review_unresolved,unintegrated_work,disposition_unproven}.v1`
— and each fires with zero audit lines written and zero Git mutation.

**Server-resolved, never caller-carried.** `releaseWorktree` gained NO public proof
parameter. It resolves the proof itself from the launcher-owned authority root
(`<main-repo>/.agent-launch/wk-terminal-disposition/<IN-XXXX>.<WK-YYYY>.json`), beside
the reaper's own audit sink and outside the repository content tree, and re-derives every
expectation it compares against. Handing the public API a structurally perfect proof
object changes nothing. The `reason` string survives as AUDIT METADATA only; it
authorizes nothing, and the accepted disposition is recorded on the audit line so an
operator can always answer "on what authority was this branch deleted".

**Minting is the disposition boundary's, not the reaper's.** Only the trusted backend
disposition boundary can observe run termination, review resolution, and slice
integration together, so it alone mints — through this module's exported closed-input
builder `buildWkTerminalDispositionProof`, which refuses an unknown key, a non-terminal
disposition, or a receipt digest that does not re-derive. Until that boundary is wired,
the resolver finds nothing and every wk/\* reap refuses `wk_terminal_proof_missing.v1`.
That is the intended fail-closed posture rather than a gap: no proof, no deletion.
`releaseWorktree` is correspondingly LATENT BY DESIGN — it has no production caller yet
and shows up in a dead-code sweep as an unwired export; it is the subject of this guard,
not dead code.

**Slice retention is TWO lifetimes, not one (decision clause 5, amended and
re-ratified 2026-07-19).** The slice WORKTREE and the slice BRANCH have different
lifetimes and must not be coupled:

- **Slice WORKTREE — reaped AT INTEGRATION.** Once a slice's commit integrates into
  the WK branch, its worktree is removed. Under clause 1(a) the slice's mandatory
  review has already completed and been accepted before integration, so the worker is
  terminated by construction of the sequence and no separate termination proof is
  required. A worktree is a RECONSTRUCTIBLE VIEW (`git worktree add` at the reviewed
  SHA recreates it) and workers hold no legitimate uncommitted state in it, so nothing
  durable is lost. Because slice worktrees are FULL (non-sparse) checkouts under
  clause 2, NOT reaping them means a long WK accumulates full checkouts for its entire
  life — the expensive direction, which is why this reap is required rather than
  optional. **It is not implemented:** as of 2026-07-19 nothing in production reaps a
  slice worktree at integration. Wiring it is required work, not existing behavior.
- **Slice BRANCH — deleted in ONE post-PR sweep.** No slice branch is deleted during
  the WK's life: not at integration, not on accepted review, not on cancellation or
  supersession. All of a WK's slice branches are deleted TOGETHER, once, AFTER the
  squashed WK PR lands — the landing IS the evidence the work survived, so no
  per-branch disposition proof, receipt, or terminal-disposition document is required
  or authorized for a slice branch. A cancelled, superseded, or abandoned slice is left
  to operator cleanup or swept with the rest at PR time. Branch accumulation during a
  long WK is accepted and cheap. **Reaping a worktree must not delete its branch.**

The rationale for the asymmetry: the branch is the SOURCE OF TRUTH and the worktree is
a DERIVED VIEW, so retention follows cost and recoverability — retain the cheap,
irreplaceable thing; reap the expensive, reconstructible one.

This SUPERSEDES the per-disposition slice-branch reaping this section previously
described (accepted review / orchestrator cancellation / orchestrator revert, each
deleting the slice branch). **`releaseRetainedSlice` still implements that superseded
per-disposition model** — including the guarded `update-ref -d` branch deletion — and
is still reachable through `runRetainedSliceCleanupDisposition` on the dispatch
run-monitor route. That divergence between the amended decision and the code is a KNOWN
OPEN GAP tracked as implementation work; this section documents the decision, not
current reaper behavior. Do not reintroduce the per-disposition branch-reaping language.

Proof B governs the parent WK branch; it is a separate contract from Proof A
(`workspace-agent-slice-review-acceptance.v1`), which is per-slice, bound to an exact
reviewed SHA, invalidated by a corrective commit, and authorizes exactly one integration.
Merging them would produce the generic token whose boolean/reason fail-open both redteams
rejected.

**Threat model — not overclaimed.** Proof B is non-forgeable within the repo's existing
trusted-loopback / honest-launcher model: it is minted only by the trusted boundary, the
reaper re-derives the tip and the record digest server-side, and the receipt digest binds
the disposition to those exact facts, so a cross-WK or stale-tip replay fails the
comparisons. It is **not** a cryptographic guarantee against a hostile process running as
the same user with write access to the launcher-owned authority root; that would require
a challenge/MAC and an operator-approved authentication-protocol expansion.

## Post-Terminal WK Forge Handoff Over The Broker (work record)

The WK forge handoff is the FOURTH same-pattern host-write operation
(`wk_forge_handoff`, response kind `wk_forge_handoff_completed`) alongside
`provision_worktree`, `commit_slice`, and `integrate_slice`. It exists so that a
terminal work record's accumulated change can be represented to the consuming
repository's forge as ONE deterministic squashed commit on a forge branch plus ONE pull
request — work that runs `git`, `gh`, and credentialed network I/O and therefore cannot
run inside the read-only, credential-stripped wiki-MCP bwrap namespace. It reuses the
already-running host-write transport and adds no listener, HTTP/URL transport,
bearer/token system, proxy, relay, daemon, second broker, generic Git API, or
worker-visible Git metadata.

**Host-only authority; thin bwrapped proxy.** The bwrapped `workspace_wk_forge_handoff`
MCP handler is a thin channel client of the existing
`AGENT_LAUNCH_HOST_WRITE_AUTHORITY_TCP_ENDPOINT`. All Git object/ref writes, remote
observation/publication, gh discovery/authentication, credential use, network activity,
branch publication, and PR operations execute in this launcher sidecar process, outside
bwrap. The pure wire contract lives in
`host-write-authority-substrate/request-envelopes-wk-forge-handoff.mjs` (bwrap-safe: no
Git/gh/credential/process logic), and the host executor lives in
`host-write-authority-substrate/broker-wk-forge-handoff.mjs`, imported and composed ONLY
by the outside-bwrap sidecar/broker path. `broker.mjs` never imports the host executor;
the sidecar supplies it as the `wkForgeHandoff` option with `forgeHandoffMainRepo` set to
the launcher-frozen `mainRepo`. A broker not composed with both refuses `wk_forge_handoff`
with `broker_forge_handoff_unavailable`.

**One `wk_forge_handoff` operation.** The request carries ONLY `{ assigned_unit }` (a
canonical `WK-####` selector). It carries no caller-selected repository, path, remote,
ref, SHA, initiative, base, head, branch, credential, gh path, Git argv, retry mode, or
merge intent; those are dropped by the request builder and the broker's exact
outer/inner envelope guards. The host broker independently resolves the launcher-owned
canonical HTTPS `origin` coordinate (one host/owner/repository binding both Git push and
gh REST — remote helpers, `url.*` rewrites, multiple push URLs, non-HTTPS destinations,
and Git/REST disagreement refuse before any credential use with
`broker_forge_handoff_remote_invalid`), proves terminal/quiescent eligibility (no
implementation slice may still advance the persistent WK ref, every integrated
contribution is represented by the WK tip, and a canonical initiative is assigned;
findings-only review slices contribute no Git content and are not a prerequisite —
agent-chassis' CCE review policy remains a separate organization-level gate),
resolves the frozen WK ref/tip and the unique merge base, and builds the deterministic
squash by reusing `wkTip^{tree}` verbatim with that merge base as the sole parent and
launcher-owned deterministic identity/message/dates (no wall clock). Canonical record
eligibility and the WK ref are re-read before every successful return.

**Credential boundary and idempotent publication.** The gh token is never read, returned,
placed on an argv or in a remote URL, or surfaced in results/errors/diagnostics/logs or
on the wire; branch publication pushes with gh's one-shot HTTPS Git credential helper so
git obtains the credential at push time. Branch publication is absent-ref CAS only (exact
head recovers, a different head or race refuses and is re-observed —
`broker_forge_handoff_publication_disagreement`); PR selection is exact
repository/base/head across bounded all-state pagination (zero creates once, one recovers
open/closed/merged, multiple/malformed/uncertain refuse). It never force-updates or
deletes a branch, or merges/rebases/resets/updates the landing branch. Before any
authenticated remote observation, absent or unauthenticated host gh returns a bounded
human-action result — a manual `git merge --ff-only` argv only when an exact local
landing branch/tip, the deterministic squash, an absent/exact local handoff-ref CAS, and
fast-forward applicability are all mechanically proven, else `human_reconciliation_required`
with no guessed branch and no merge command. After authenticated remote observation
begins every failure is fail-loud (`broker_forge_handoff_indeterminate`) and cannot
degrade to a manual success. The adapter forwards a broker refusal, and validates the
returned result against the exact closed per-kind schema (binding `assigned_unit` back to
the request and proving losslessness) before deep-freezing it, failing closed with
`host_write_authority_forge_handoff_result_invalid` otherwise.

**Threat model — not overclaimed.** This is the same trusted-loopback / honest-launcher
model as the other host-write operations: the token stays inside gh and the credential
helper, only `assigned_unit` crosses the wire, and the host broker re-derives every
authority fact server-side. It is **not** a cryptographic guarantee against a hostile
same-UID operator, and it adds no broker-authentication hardening.
