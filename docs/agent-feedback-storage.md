# Agent feedback storage architecture

Maintainer reference for repository binding, append effects and runtime provenance. This document is not advertised as submission guidance.

One persistent SQLite database at the primary checkout's `.agent-launch/feedback.sqlite` serves a Git repository and every session, agent and linked worktree. It is uncommitted runtime data. The database stays in place: binding a session never moves, deletes, resets or recreates existing storage or changes existing reports and session handles.

The launcher supplies its selected repository separately from managed execution/provisioning checkouts. MCP startup selects that repository through the existing workspace configuration (`WIKI_MCP_WORKSPACE_DIR`, or `WIKI_MCP_REPOS` plus `WIKI_MCP_WORKSPACE_ALIAS`). Feedback captures the selected repository's primary checkout and Git common-directory identity at tool registration. Submissions revalidate that binding and the fixed storage paths against the surviving primary, without resolving the execution checkout again. Deleting a managed checkout while a server is alive therefore leaves its feedback session usable, even when the server started in that checkout. A new server can initialize after execution-checkout deletion when its authoritative configuration still selects the primary repository; a missing execution path alone cannot supply repository identity. There is no feedback-specific repository or storage override.

Primary resolution uses common-directory identity and worktree metadata, including nested/symlink-normalized paths and relocated Git directories. Git's first worktree-list entry identifies the primary, whose Git directory and common-directory ownership are validated directly. Linked checkout paths are never probed to locate or revalidate primary storage: missing directories and prunable directories without `.git` cannot block initialization or later operations. Feedback never prunes their metadata or deletes their directories. Each operation verifies that the primary still owns the captured common directory. An unavailable or replaced primary refuses, and unrelated repositories remain isolated. Bare, non-Git, ambiguous and inaccessible layouts fail specifically, without selecting HOME, cwd, guessed parents, global storage or worktree-local substitutes. The fixed storage paths reject symlinks, shared files and tracked database collisions on every operation. Feedback changes no tracked content, refs, assignments, WKs or review results. Existing repository runtime-ignore ownership covers `.agent-launch/`.

Runtime assigns UTC timestamps and immutable per-observation provenance: executing `@agent-chassis/wiki-core` name/version from its own installed manifest; optional `@agent-chassis/core` distribution name/version from the existing core carrier; actual `cli`/`mcp` transport and role only when known. Core CLI and MCP use the same raw package carrier for provenance, independently of whether its documentation bundle can be bound or read. Standalone wiki-cli records `core_package: null` and unknown CLI role as null. Package versions can differ. Caller fields, consumer manifests, cwd, remotes and MCP server version cannot substitute for package provenance. Continuing a session after upgrading appends new provenance without relabeling earlier reports. Missing/malformed executing manifests fail explicitly.

A new session and its first observation commit atomically. Acknowledged submissions append distinct rows; concurrent processes lose none. SQLite uses DELETE journaling, FULL synchronous writes, foreign keys and zero driver busy timeout. Feedback retries only safe pre-effect exclusive-lock acquisition, at 25 ms polls within 1,000 ms. It never retries an insert or uncertain commit. A receipt is returned only after commit. Retrying after a lost receipt can duplicate feedback: no exactly-once or semantic deduplication guarantee exists.

Errors use declared `feedback_*` mechanical codes with the actual cause, subject, known effect and supported correction or stopping point. A failure before commit never claims saving; no failure rebuilds or deletes storage. Commit busy with an active transaction is rolled back as `not_committed`. An uncertain commit reports `possibly_committed` and tentative session/feedback IDs without claiming success or automatically retrying. Retain those IDs; they do not establish persistence.

Repository-resolution refusals preserve the selected repository and the actual filesystem or failed Git operation's cause and exit facts. Command arguments and duplicate diagnostic wrappers stay internal. Submission-schema refusals use the feedback domain validator's field constraints instead of serializing SDK issue carriers or rejected enum/type values. The published schema and domain validator both require string session and related-feedback identities; arrays cannot be coerced into identities.

The next normal legitimate feedback write can recover a pending SQLite journal and preserve committed observations. Do not fabricate a report solely for recovery, change permissions as a journal remedy, or delete/reset storage.

Feedback exposes recording only. There is no feedback read tool, resource, CLI inspection command, dashboard or export route. Receipts acknowledge recording and return session/feedback IDs without inspection links. There is no retention policy, automatic pruning, telemetry upload, automatic detection or WK creation.

A successful commit followed by a close failure reports `saved:true`, `effect:committed`, the session/feedback identities and the specific cleanup failure. It must not label those identities tentative or invite a second append. A repository-binding failure captured at registration remains unavailable in that server; no agent rebind or restart call exists. Stop advisory reporting and continue unrelated work.

## Local CLI adapter

Use CLI only, without MCP: `wiki feedback add --stdin --new-session --json`, then `--session <returned-session_id>`. Stdin contains the report, not the MCP envelope. `--dir` selects the authorized local repository. CLI raw stdin accepts at most 256 KiB; `feedback_stdin_too_large` can be corrected by losslessly minifying the same JSON. That remedy does not fix `feedback_report_too_large`.
